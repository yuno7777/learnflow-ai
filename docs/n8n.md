# n8n integration

## Model

n8n is the primary execution engine. LearnFlow always owns the `workflow_executions` row —
n8n owns the steps. When a workflow has an `n8n_webhook_path`, LearnFlow POSTs a signed
payload and leaves the run `running` until n8n calls back. When n8n is not configured or does
not answer, the built-in runner executes the equivalent steps locally, and the execution row
records which path was taken.

That fallback is deliberate: the demo, the tests and CI must not depend on a live n8n, and a
production outage should degrade rather than stall.

## The five workflows

| File | Trigger | Steps |
|---|---|---|
| `01-learner-onboarding.json` | Webhook `learnflow/learner-onboarding` | verify signature, fetch learner, generate welcome message, send email, record activity, signed callback |
| `02-inactive-learner-reminder.json` | Cron, daily 07:00 | fetch inactive learners, split, check reminder limit, draft nudge and send, or open an escalation ticket |
| `03-support-ticket-triage.json` | Webhook `learnflow/ticket-triage` | verify, fetch ticket, RAG retrieval, branch on confidence, escalate or mark triaged, signed callback |
| `04-document-processed.json` | Webhook `learnflow/document-processed` | verify, fetch document, branch on status, notify admins or retry ingestion, signed callback |
| `05-weekly-analytics-summary.json` | Cron, Mondays 08:00 | overview plus usage plus workflow stats, compose digest, email |

They are generated by `scripts/build_n8n_workflows.py`. Five workflows share the same
signature-verification and callback-signing code, and keeping it in one place means a change
to the signing scheme cannot drift between files. CI fails if the JSON drifts from the script.

## Importing

1. **Workflows → Import from file**, one per file in `automation/n8n-workflows/`.
2. Activate each one.
3. Set the environment variables the Code and HTTP nodes read (already wired in
   `docker-compose.yml`):

| Variable | Purpose |
|---|---|
| `LEARNFLOW_API_URL` | Base URL of the API (`http://api:8000` inside compose) |
| `LEARNFLOW_API_KEY` | API key created in LearnFlow so n8n can call the API |
| `LEARNFLOW_WEBHOOK_SECRET` | Must equal `WEBHOOK_SIGNING_SECRET` |
| `LEARNFLOW_ADMIN_EMAIL` | Recipient for notifications |
| `LEARNFLOW_EMAIL_FROM` | Sender address |
| `LEARNFLOW_INACTIVITY_DAYS` | Threshold for the reminder workflow |
| `NODE_FUNCTION_ALLOW_BUILTIN=crypto` | Lets Code nodes require the crypto module |

4. In LearnFlow, create a workflow from the matching template and set its webhook path.

## Signing

Outbound (LearnFlow to n8n) and inbound (n8n to LearnFlow) use the same scheme:

```
X-LearnFlow-Signature: t=<unix seconds>,v1=<hex hmac-sha256>
mac = HMAC_SHA256(secret, f"{t}.{raw_body}")
```

The n8n webhook nodes are configured with `rawBody: true` because the mac covers the exact
bytes — verifying against a re-serialised copy fails on key order or whitespace alone.

Three defences, not one:

1. **Constant-time comparison**, so there is no timing oracle on the mac.
2. **Freshness window** of plus or minus 300 seconds, so a captured request expires.
3. **Replay store** — the mac is inserted into `webhook_receipts` under a unique constraint,
   so a replay inside the window is rejected by the database, not by application logic.

## Callback payload

```json
{
  "execution_id": "uuid",
  "status": "succeeded",
  "n8n_execution_id": "4242",
  "output": { "welcome_sent": true },
  "steps": [
    { "name": "n8n:send_email", "kind": "email", "status": "succeeded",
      "output": { "to": "learner@example.com" }, "duration_ms": 120 }
  ],
  "input_tokens": 812,
  "output_tokens": 96
}
```

Applying a callback is idempotent: a duplicate for an already-finished execution is a no-op.

## Reconciliation

If n8n crashes mid-run the callback never arrives. A cron task in the worker
(`sync_n8n_executions`, every five minutes) reads still-running executions that carry an
`n8n_execution_id` back from the n8n REST API and closes them out. This needs `N8N_API_KEY`.

## Failure handling

- A workflow that raises records the failing step with its error, marks the execution
  `failed`, and re-raises so ARQ applies its retry policy.
- `POST /executions/{id}/retry` increments `retry_count` and re-queues.
- In the inactivity workflow, one learner failing does not abort the batch — the step row
  records why and the loop continues.
